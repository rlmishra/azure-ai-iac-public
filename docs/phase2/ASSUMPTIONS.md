# Phase 2 decisions recorded before implementation

- Base: verified private GitHub branch phase1-azure-foundation at c5ae5bedbb527c55f68f3dd23ef7769778dab12f. No AGENTS.md found in workspace or checkout. Work proceeds in an isolated worktree on phase2-microsoft-foundry; the original Phase 1 directory and ZIP remain untouched.
- Preserve Terraform 1.17.2, AzureRM 5.13.0, lock files and existing Phase 1 resource addresses. Installed schema and pinned provider documentation support current AIServices account/project/model resources. No provider upgrade or AzAPI is needed.
- Use Microsoft.CognitiveServices/accounts (AIServices, S0, project management enabled) and accounts/projects. Do not use Microsoft.MachineLearningServices hub/project resources exposed by azurerm_ai_foundry/azurerm_ai_foundry_project.
- Foundry is opt-in (null configuration by default). Projects are explicitly named; model deployments require separate activation and an explicit approval catalog including format, name, version, permitted locations, permitted SKUs and capacity ceilings. An empty catalog/deployment map makes no model/capacity choice.
- Missing organizational inputs: actual subscription/tenant, globally unique account/subdomain, approved regions/model versions/SKUs/capacity, quota/entitlement, network/DNS design, approved principals, project data-access grants, diagnostic category availability, retention/redaction and recovery requirements. Examples/tests are illustrative, never approval.
- One Foundry account per enabled environment, in the foundation region. Public Azure cloud only. Existing foundation modules remain owners of DNS/private endpoints, monitoring and supporting data resources. Add the three documented Cognitive/Foundry/OpenAI private zones and one account private endpoint when enabled.
- All accounts/projects use system-assigned identities; the pre-existing application user-assigned identity can receive explicit, opt-in OpenAI inference access. New roles are implemented inside the Foundry module without widening Phase 1's generic identity-role allowlist.
- Use verified stable built-in role GUIDs for Foundry User (formerly Azure AI User) and Cognitive Services OpenAI User. Current Microsoft documentation notes role-name rollout; GUIDs avoid reliance on renamed display names. Grants are resource/project scoped and never automatically give humans Owner/Contributor.
- Project account access, Key Vault secret-read and storage blob-read permissions require explicit per-project approval. These RBAC grants do not wire an agent runtime, mount storage, create secrets or bypass private service firewalls. They do not imply a working standard-agent network setup.
- No resource key values, data-plane secrets, agent deployments, managed online endpoints, search indexes, fine-tuning, content-filter customization, serverless marketplace billing agreements or Gravitee configuration are in this phase.
- Restrict service outbound access, deny network ACLs with no trusted-service bypass, disable public access and local/API-key authentication. Advanced tools requiring outbound/network injection remain unsupported until independently designed and approved.
- Azure-managed encryption is the baseline. Customer-managed keys and enterprise policy mappings remain separate design decisions. No multi-region application failover or DR is implemented.
- All Terraform tests are mocked plan-only tests; no Azure identity or approved backend is available. No real Azure plan, apply, destroy or production-secret access will run. Provider/API shape validation cannot establish model availability, quotas, policy compliance, endpoint reachability or runtime authorization.
